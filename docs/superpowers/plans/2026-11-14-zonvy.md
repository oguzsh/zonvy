# Zonvy Implementation Plan

> **Execution mode: you build it, Claude mentors.** You write every line. Each task ends with a **Bring to mentor** checkpoint: share your diff, test output, or a screenshot, and we review it together before you move on. Ask for hints, explanations, or a code review at any point; Claude won't write the code for you unless you ask. Track progress with the checkboxes.

**Goal:** A tray/menu bar app for macOS, Windows, and Linux that shows the current local time of any city with ≥15k people, fully offline, with pinnable favorites.

**Architecture:** Tauri 2 with a Svelte + TypeScript frontend. City data (from GeoNames) is generated at dev time into a JSON file bundled with the UI. Search and time math run in TypeScript, using `Intl` and the OS's IANA time zone data. Rust stays thin: tray icon, popover window, launch at login, global shortcut, single-instance, and reading the OS 12h/24h preference.

**Tech Stack:** Tauri 2, Rust (stable), SvelteKit in SPA mode (`adapter-static`, `ssr = false`, the official Tauri template) + Svelte 5 + TypeScript + Vite, Vitest, pnpm. Plugins: `positioner`, `global-shortcut`, `autostart`, `store`, `single-instance`; `window-vibrancy` crate (macOS).

**Spec:** [`docs/superpowers/specs/2026-11-14-city-time-design.md`](../specs/2026-11-14-city-time-design.md). Read it alongside this plan.

## Global Constraints

- **No network requests at runtime**, ever. GeoNames is downloaded only by the dev-time script.
- City data: GeoNames `cities15000`, bundled file **≤ 2 MB** uncompressed.
- About screen text includes: **"City data © GeoNames, CC BY 4.0"**.
- Offset format: `+3h`, `−5h30`, `+5h45`, `±0h`. Use the real minus sign `−` (U+2212).
- Shortcut defaults: **⌃⌥Z** (macOS), **Ctrl+Alt+Shift+T** (Windows/Linux), on by default, on/off only.
- Popover ~300 px wide, "A · Native" look, light/dark follows the system, tabular numerals.
- Popover is created once and shown/hidden, never re-created.
- Unsigned builds: `.dmg` (universal), NSIS `.exe`, `.AppImage` + `.deb`.
- Out of scope: Mac App Store, auto-updater, mobile.

## Review Focus

The spec implies these five cases, and they're the most likely to bite you in daily use. Each one has a test in the task that owns that code.

1. **You travel or change your system time zone while the app runs.** The "you" offset must follow the new zone without restarting the app. → Task 3 and Task 4.
2. **A DST change happens while the popover is open.** The city time must jump correctly at the next tick. → Task 3.
3. **Half-hour and quarter-hour zones** (Kolkata +5:30, Kathmandu +5:45, Adelaide +10:30 / +9:30). → Task 3.
4. **Punctuation and spelling variants:** "st louis" for "St. Louis", "hochiminh" or "ho chi minh". → Task 2.
5. **A pinned city that's no longer in the dataset**, or an unknown zone id, after you regenerate the data. It must be skipped or shown as "—", never crash the app. → Task 3 and Task 5.

## Phase 2 — Core logic (pure TypeScript, test-first)

### Task 2: Normalization + search

**Learn first:** `String.prototype.normalize("NFD")` and stripping combining marks (`\p{M}` regex with the `u` flag). Also why a search index is precomputed once.

**Files:**
- Create: `src/lib/cities/normalize.ts`, `src/lib/cities/search.ts`
- Test: `src/lib/cities/normalize.test.ts`, `src/lib/cities/search.test.ts`

**Interfaces:**
- Consumes: `City` (Task 1).
- Produces: `normalize(s: string): string`. Lowercases, strips accents, turns punctuation into spaces, collapses whitespace, and trims.
- Produces: `createSearch(cities: readonly City[]): (query: string, limit?: number) => City[]`. The default `limit` is 20.

**Ranking:**
1. Normalized name starts with the query.
2. Any word in the name starts with the query.
3. Name contains the query anywhere.

Ties are broken by `pop`, highest first. Match against both `name` and `ascii`, and also against the name with spaces removed (so "hochiminh" works).

- [ ] **Write failing tests:**
  - `normalize("São Paulo")` → `"sao paulo"`.
  - `normalize("St. Louis")` → `"st louis"`.
  - `normalize("  New   York ")` → `"new york"`.
  - Searching `"sao paulo"` returns São Paulo, BR, first.
  - `"portland"` returns at least 2 results with different `admin1` values. Oregon comes first (higher population).
  - `"york"`: "York, GB" (prefix) ranks above "New York" (word-prefix), even though New York has a far bigger population.
  - `"st louis"` finds St. Louis, US-MO.
  - `"hochiminh"` finds Ho Chi Minh City.
  - `""` and `"   "` return `[]`.
  - `"a"` returns exactly 20 results; with `limit` 5 it returns 5.
  - Performance: 1,000 searches against the full `cities.json` finish in under 1 s (that's under 1 ms each).
- [ ] Run the tests. Expected: FAIL.
- [ ] Implement both functions. `createSearch` normalizes every city once up front.
- [ ] Run the tests. Expected: PASS.
- [ ] Commit: `feat: accent-insensitive city search with ranking`.

**Bring to mentor:** your ranking code. We'll review readability and whether any tie-break feels wrong when you try real queries.

### Task 3: Time math & formatting

**Learn first:**
- `Intl.DateTimeFormat` with the `timeZone`, `timeZoneName: "longOffset"`, and `hourCycle` options.
- Why you never add hours to a `Date` by hand for another zone.
- What a DST transition looks like in UTC.

**Files:**
- Create: `src/lib/time/zone.ts`, `src/lib/time/format.ts`
- Test: `src/lib/time/zone.test.ts`, `src/lib/time/format.test.ts`

**Interfaces:**
- Produces: `offsetMinutes(instant: Date, tz: string): number`. Minutes east of UTC, e.g. `Asia/Kathmandu` → `345`.
- Produces: `relativeOffsetMinutes(instant: Date, cityTz: string, localTz: string): number`.
- Produces: `formatOffset(minutes: number): string`, e.g. `180` → `"+3h"`, `-330` → `"−5h30"`, `0` → `"±0h"`.
- Produces: `dayTag(instant: Date, cityTz: string, localTz: string): string | null`. Returns the short English weekday (`"Sat"`) when the calendar dates differ, otherwise `null`.
- Produces: `formatClock(instant: Date, tz: string, hour12: boolean): string`, e.g. `"02:42"` or `"2:42 AM"`.
- Produces: `isValidZone(tz: string): boolean`.
- Every function takes `localTz` as a parameter. **No function may cache the local zone** (Review Focus 1).

- [ ] **Write failing tests.** Use fixed instants only:
  - `offsetMinutes(2026-01-15T12:00Z, "Asia/Kathmandu")` → `345`.
  - `offsetMinutes(2026-01-15T12:00Z, "Asia/Kolkata")` → `330`.
  - `offsetMinutes(2026-01-15T12:00Z, "Australia/Adelaide")` → `630`.
  - **DST:** `America/New_York` gives `-300` at `2026-03-08T06:59Z` and `-240` at `2026-03-08T07:01Z`.
  - **Gap weeks:** NY − London is `-300` on 2026-03-05 and `-240` on 2026-03-20. (The US moves its clocks forward on March 8, the UK on March 29.)
  - `formatOffset`: `180` → `"+3h"`, `-330` → `"−5h30"`, `345` → `"+5h45"`, `0` → `"±0h"`, `1020` → `"+17h"`.
  - At `2026-11-13T17:42Z` (Fri), local `America/Los_Angeles`: `dayTag` for `Asia/Tokyo` is `"Sat"`; for `Europe/London` it's `null`.
  - Changing `localTz` in the same call changes the result. With `cityTz` `Asia/Tokyo` at a fixed instant, `relativeOffsetMinutes` gives `1020` from `America/Los_Angeles` and `360` from `Europe/Istanbul`.
  - `formatClock(2026-11-13T17:42Z, "Asia/Tokyo", false)` → `"02:42"`.
  - `isValidZone("Mars/Olympus")` → `false`, and none of these functions are called with it in a way that throws (Review Focus 5).
- [ ] Run the tests. Expected: FAIL.
- [ ] Implement the functions. Derive `offsetMinutes` by parsing the `longOffset` part (`"GMT+05:45"`) from `formatToParts`.
- [ ] Run the tests. Expected: PASS.
- [ ] Commit: `feat: offset, day tag and clock formatting`.

**Bring to mentor:** the test file. We'll check together that the DST instants really cross the transition.
